# v2.3 — The lupa spike

**Date:** 2026-11-20
**Issue:** GOLEM-018 (#18)
**Question:** can lupa's Lua 5.4 runtime carry the interpreter design in ARCHITECTURE §Robot language and the
sandbox and §Execution, budgets and the report?

**Answer: GO with lupa 2.8 (`lupa.lua54`), pinned.**
- Checks 1–5 pass, so the design gate is clear.
- Check 6 found two things that change the plan:
  - **F1:** the `python` table, which the sandbox removes (GOLEM-019);
  - **R1:** C functions run without the count hook, which is an open risk; the owner decides it before
    v4.1.

The spike ran as a scratch script against the project's environment: macOS arm64, Python 3.12.12.
The code below is quoted from it, and the outputs are as printed. The answers the code relies on are kept as
tests in `tests/test_lua_runtime.py`.

## 2. Coroutines driven from Python

A small driver chunk, run in the runtime's globals, loads the program into a fresh environment, wraps it in a
coroutine, and returns a `step(value)` function to Python. Python calls `step` with the last result and gets
back `("cmd", cmd, arg)`, `("done", value)` or `("error", value)`.

```lua
function(src)
  local env = {}
  env.look = function(d) return coroutine.yield({cmd = "look", arg = d}) end
  local chunk = assert(load(src, "=program", "t", env))
  local co = coroutine.create(chunk)
  return function(value)
    local ok, a = coroutine.resume(co, value)
    if not ok then return "error", a end
    if coroutine.status(co) == "dead" then return "done", a end
    return "cmd", a.cmd, a.arg
  end
end
```

The program called `look('N')` 5000 times, and Python answered `"wall"` every time:

```
commands: 5000 | end: done 5000 | 1.9 us per command round trip
```

- **The answer:** the yield returns Python's value, the fields come back as plain Python strings, and a round
  trip costs about 2 µs. A 200-step level spends well under a millisecond in the exchange.
- **The way the driver will work:** Lua-side `coroutine.resume` through the driver chunk, not lupa's own
  coroutine wrapper (`function.coroutine()`, which Python resumes with `send`). Two reasons:
  - the count hook must be set on the coroutine object in Lua, with `debug.sethook(co, …)`;
  - the sentinel must be compared in Lua (see 3).

  The driver chunk keeps `coroutine`, `debug` and the sentinel in its upvalues, where the program cannot
  reach them.

## 3. Count hooks per coroutine and the sentinel

```lua
function(src, every, budget)
  local SENTINEL = {}
  local counter, main_ticks = 0, 0
  local env = {error = error}
  local chunk = assert(load(src, "=program", "t", env))
  local co = coroutine.create(chunk)
  debug.sethook(co, function()
    counter = counter + every
    if counter >= budget then error(SENTINEL, 0) end
  end, "", every)
  local ok, err = coroutine.resume(co)
  for i = 1, 100000 do main_ticks = main_ticks + 1 end   -- the main state is not hooked
  return ok, rawequal(err, SENTINEL), type(err) == "string" and err or tostring(type(err)), counter
end
```

```
infinite loop:       (False, True, 'table', 1000000)
own error string:    (False, False, 'program:1: instruction budget exhausted', 0)
short program:       (True, False, 'nil', 0)
python identity of one table through two proxies: False | ==: False
```

- **The hook stays on its coroutine.** It fires only inside the coroutine it was set on: the main state's
  100 000-iteration loop did not move the counter past the budget.
- **The sentinel ends the run.** An `error(SENTINEL)` raised from the hook ends the coroutine with exactly
  that value, and `rawequal` recognizes it.
- **A program's own error is not the sentinel.** `error("instruction budget exhausted")` is a different
  value, a string with `program:1:`.
- **The comparison stays in Lua.** Python sees two different proxy objects for one Lua table (`is` and `==`
  are both false), so an identity check in Python would never match.

## 4. `max_memory`

```
direct: LuaMemoryError:
inside a coroutine, coroutine.resume gives: (False, 'not enough memory')
same runtime afterwards: 2 | a new runtime: 4
```

- A runtime with `max_memory = 1 MiB` refuses a 4 MiB `string.rep`.
  - **Run directly:** the error reaches Python as `lupa.lua54.LuaMemoryError`, with an empty message.
  - **Inside the program's coroutine:** `coroutine.resume` catches it and returns `false, "not enough
    memory"`. That is the path the driver will see, and its report text is `"not enough memory"`.
- The same runtime goes on working afterwards, and so does a new one.

## 5. The determinism problems, reproduced and removed

| Source | Reproduced | Prototype fix | After the fix |
|---|---|---|---|
| `pairs` order (string-hash seed per runtime) | 2 distinct orders of a 24-key table over 30 runtimes in one process | iterate sorted keys: numbers, then strings, then `false`, `true` | 1 order |
| `table.sort` pivot (`l_randomizePivot` from `clock()` and `time()`, used once a partition of more than 100 elements turns unbalanced) | "organ pipe" and "median-of-three killer" inputs of 20 000 records: 15 distinct results (order of equal keys and comparator calls) over 15 runtimes; a sawtooth input did not vary | a stable bottom-up merge sort in Lua | 1 result, 149 213 comparator calls every time |
| `tostring` of a table | the same address over 10 runtimes in one process (the allocator reuses it), but different across processes: `0xb90c0ca00`, `0x93cc1c200`, `0x8d2c0ca00` | return the type name for a table, function, thread or userdata | `"table"` |
| `string.format` `%p`, and `%s` of a table | 7 and 3 distinct values over 10 runtimes | a wrapper that refuses `%p` with a Lua error and passes `%s` arguments through the safe `tostring` | `"table-3"`; `%p` refused |
| `math.random` seed (`time(NULL)` and the state's address) | equal within one process and second, different across processes: 569250, 242680, 411813 | the driver calls `math.randomseed(RANDOM_SEED)` | 1 value over 10 runtimes |

The prototypes are scratch code. The real versions are built in v4.1, and until then v2.3's environment
leaves out `pairs`, `tostring`, `string.format`, `table.sort` and `math.random`.

### F1 — lupa keeps a `python` table in the globals, and it reaches Python objects

`register_eval=False` and `register_builtins=False` remove `python.eval` and `python.builtins` only. The
table `python` itself stays in the runtime's globals, with `as_attrgetter`, `none`, `iter` and more.
`python.none` is Python's `None`, and `python.none.__class__` is `NoneType`. From a class, Python's object
graph leads to every module, so **any Lua code that can reach this table can leave the sandbox.**

- **Today the program cannot reach it.** Its environment is a fresh table, and nothing in it leads back to
  the globals.
- **Defence in depth (GOLEM-019):** the sandbox sets `python = nil` in the runtime's globals right after
  creating the runtime, before any program text is loaded. lupa keeps working afterwards: Lua calls,
  Python-to-Lua calls and table conversion all work.
- **The pin:** a test asserts that `python` is `nil` after the sandbox is built.
- **The document:** ARCHITECTURE's sentence "so that Lua has no `python` module" is corrected in GOLEM-019,
  with the implementation and its test.

### Errors and counts

- **Errors carry their line.** With the chunk name `"=program"`, syntax and run-time errors start with
  `program:<line>:`.
- **Instruction counts are exact on the hook's grid.** An empty numeric `for` loop costs one instruction per
  iteration: 1000 iterations count 1000, and 100 000 count 100 000. Counts are exact to `HOOK_EVERY`.

### R1 — an open risk: C functions run without the count hook

```
string.find over 50 chars with four '.-': 0.02 s, hook calls: 0
string.find over 100 chars with four '.-': 0.45 s, hook calls: 0
string.find over 200 chars with four '.-': 13.07 s, hook calls: 0
```

**The mechanism.** The count hook fires only between Lua VM instructions. One call into a C function, such as
the pattern matcher behind `string.find`, `string.match`, `string.gmatch` and `string.gsub`, runs to its end
without a hook.

**The danger.** A pattern with several `.-` backtracks polynomially (here about n⁴), so a single call over a
few hundred characters runs for minutes and ignores the instruction budget. Memory-heavy calls
(`string.rep`, `table.concat`) are stopped by `max_memory` instead.

**What it means now.** For the owner's `golem-local` in v2.3 this is a slow run that Ctrl+C ends. For the
server from v5.1 it would be one program holding the server.

**Options (the owner decides before v4.1, which completes the sandbox):**
- **(a) Remove the pattern functions.** Remove `find`, `match`, `gmatch` and `gsub` with patterns: keep
  `string.find(s, plain, init, true)` only, through a wrapper that forces `plain`. This is simple, and it
  changes the robot language contract.
- **(b) Run each program in a worker process** with a wall-clock limit. This catches every C-level stall,
  and it costs a process per run and changes how the server and `golem-local` hold a run.
- **(c) Keep the patterns,** with a cap on the subject's length (for example 256 bytes) for the pattern
  functions. This limits the worst case without removing the feature; the cap needs measuring.

Until that decision, v2.3 keeps the string library as ARCHITECTURE lists it, without `dump` and `format`.

## Go / no-go

**GO.** lupa 2.8 with `lupa.lua54`:
- installs from wheels;
- lets Python drive coroutines at about 2 µs per command;
- gives per-coroutine count hooks with a sentinel that only the driver can recognize;
- enforces `max_memory`;
- loads text only.

Every determinism problem was reproduced, and each is removed by its planned fix.

**Carried forward:**
- **F1:** remove `python` from the globals, in GOLEM-019.
- **R1:** the owner decides on C-level stalls before v4.1.
