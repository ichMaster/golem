## Findings

### 1 — 🔴 C functions run without the count hook (spike R1)

**Anchor:** `golem/interp/sandbox.py`. `string_library` keeps `find`, `match`, `gmatch` and `gsub`.

**Failure scenario:**
- `string.find(string.rep("a", 200), ".-.-.-.-b")` ran for 13 s with no hook call (the spike).
- At 300 characters it runs for minutes, and the instruction budget never fires.
- **v2.3:** a slow `golem-local` run, which Ctrl+C ends.
- **From v5.1:** a program that holds the server.

**Proposed fix:** one of the three options in ARCHITECTURE §Open decisions:
- (a) drop the pattern functions and keep a plain `find`;
- (b) run each program in a worker process with a wall-clock limit;
- (c) cap the subject's length for the pattern functions.

**Why deferred:** it is a design decision that changes the robot language or the run model. It is already
recorded as the owner's decision before v4.1, which completes the sandbox, and it must be settled before
v5.1 serves runs. **DEFER → v4.1**.

### 2 — 🟠 The `error` text has no cap

**Anchor:** `golem/interp/report.py` (`lua_error`), and `describe` in `golem/interp/driver.py`.

**Failure scenario:**
- `error(string.rep("x", 5 * 1024 * 1024))` gives a report whose `error` is 5 242 891 characters long. Load
  errors behave the same: Lua quotes an unfinished string literal whole in its syntax error.
- `golem-local` prints it today.
- **From v4.2:** the same text reaches the agent's snapshot.
- **From v5.1 and v5.2:** it reaches the agent through the CLI and is stored in the journal. One program
  could flood the agent's context or bloat the journal.
- `give_up` already has a cap of 200 characters.

**Proposed fix:**
- Cut every error text to 500 characters in `lua_error`, after the UTF-8 cleaning.
- Cut it in Lua first, at 2000 bytes before `safe_text`, so that megabytes never cross into Python.
- Record the cap in the report contract.
- **Regression test:** a 5 MB `error(...)` and an unfinished 1 MB string literal both give an `error` of at
  most 500 characters, with the `program:<line>:` prefix kept.

### 3 — 🟡 ROADMAP lags the releases

**Anchor:** `specification/ROADMAP.md`, the status table and v2.2's `**Status:**` line.

**Failure scenario:**
- `VERSION` is 2.2.0 and the tag `v2.2.0` exists, yet ROADMAP says v2.2 is "⏳ planned".
- The v1.3.0 and v2.1.0 release commits updated the roadmap; v2.2.0's did not, and `/release-version` does
  not name the roadmap among its files.
- A reader, or `/ship-phase`'s planning, sees a released phase as pending.

**Proposed fix:**
- Mark v2.2 as released in v2.2.0.
- **Regression test:** a test that reads `VERSION` and the roadmap, and requires every phase up to
  `VERSION`'s `A.B` to say "✅ released" and no later phase to.
- `/release-version`: list the roadmap's status lines among the files a release updates.

### 4 — 🟡 A missing levels directory reads as "unknown level"

**Anchor:** `golem/local.py` (`_run`). `list_levels` returns `[]` for a missing root.

**Failure scenario:** `GOLEM_LEVELS_DIR=/nonexistent golem-local run training/tier1/t1-01 …` prints
`{"error": "unknown_level", "detail": "unknown level"}`. The real cause, a wrong levels directory, is
hidden.

**Proposed fix:** refuse a root without `training/` with `level_error` and the path, as `golem-server`
does at start. It is the owner's hand tool and the message is merely unhelpful, so **DEFER → backlog**.

### 5 — 🟡 A UTF-8 BOM breaks a program

**Anchor:** `golem/local.py`. The program is read with `read_text(encoding="utf-8")`.

**Failure scenario:** an editor that writes a BOM produces a program whose report is `program:1:
unexpected symbol near '<\239>'`.

**Proposed fix:** read with `utf-8-sig`, or strip a leading U+FEFF. The `golem` CLI (v5.1) is where
programs arrive from the agent, and the same rule belongs there, so **DEFER → v5.1** for both readers.

### 6 — 🟡 `HOOK_EVERY` is unbounded

**Anchor:** `golem/interp/config.py`, `_positive_int`.

**Failure scenario:** with `HOOK_EVERY=1000000000`, the first hook call comes after a billion
instructions, so an endless loop runs for seconds past a 1 000 000-instruction budget before the run
ends.

**Proposed fix:** refuse a value above the smallest tier's instruction budget, or above a fixed ceiling
such as 100 000. It is owner configuration, not a program's choice, so **DEFER → v4.1** with the rest of
the budget settings.

- **Verification:** both driver tests failed on the old code. The unfinished-string error was 1 048 613
  characters long. With the fix, 524 passed.

## What's solid

- **The sandbox holds.** Every one of the 32 names that must be absent is `nil`, `_ENV.python` and
  `_ENV._G` included, and metatables are unreachable, through `string` or through a string.
- **No Python object enters Lua.** Every robot-command result is a Lua `boolean`, `string` or `integer`.
  `encoding=None` was rejected precisely because it would turn Python strings into Python objects inside
  Lua.
- **F1 is closed.** The `python` table that lupa leaves in the globals, and through which
  `python.none.__class__` reaches Python classes, is removed before any program text exists, and a test
  pins it.
- **The budget sentinel is sound:**
  - it is recognized with `rawequal` in Lua;
  - a program's own `error("instruction budget exhausted")` is an ordinary error;
  - the hook also fires inside Lua callbacks of C functions;
  - a robot command inside such a callback fails cleanly ("attempt to yield across a C-call boundary").
- **Every ending is one report:**
  - the memory cap gives "not enough memory";
  - a bug in the driver gives `internal`;
  - invalid UTF-8 is cleaned in Lua;
  - in each case the next run in the same process works.
- **Deterministic:** every fixture and every inline program gives a byte-identical report twice; the report's
  key order is fixed; lupa is pinned.
- **The hand tool is safe and the solver honest:**
  - `golem-local` refuses hidden and unknown ids alike, never changes its own environment when reading
    `.env`, and keeps the 0/1/2 exit codes;
  - `t1_solver.lua` solves all three tier-one levels with the robot API alone and no level-specific hint.
