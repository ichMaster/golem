## Findings

### 1. 🔴 HIGH — A program text that does not fit in the free Lua memory aborts the process

**Where:** `golem/interp/sandbox.py`, `Sandbox.load`. It is reached from `Run._load`, at the start of a run
and at every swap.

**Failure scenario:**
- **The cause:** lupa pushes a Python string into Lua before its protected call. When that allocation
  fails, Lua has no error handler to unwind to: it prints `PANIC: unprotected error in call to Lua API
  (not enough memory)` and calls `abort()`.
- **At the start of a run:** with `LUA_MAX_MEMORY` at 2 MiB, a 3 MiB program text kills the process.
  - In `golem-local` that is the runner.
  - In the server (`POST /api/programs/{name}/run`) it is the whole server, with the human game.
  - With the default 64 MiB cap, it takes a program file over about 64 MiB.
  - It was reproduced on v2.4.0's code, so it has existed since v2.3.
- **At a swap (new in v2.5):** the first program can leave `memory` nearly full and give up. Then even a
  5 KB text for the second program kills the process.
  - The probe pushed 5000 bytes with 8 bytes of room, and the process aborted.
  - `memory` belongs to the run, so the first program's data stays allocated.
- **Who can reach it:**
  - today, a program file that the owner puts in `programs/` or passes to `golem-local`;
  - from v5.1, the agent sends program text to the server.
  - A server crash is 🔴 HIGH by default.

**What is not a finding:**
- Strings of 30 and 200 bytes were pushed with 8 bytes of room and did not panic; lupa has enough slack
  for small allocations.
- The robot's results (`"wall"`, `"box_on_goal"`, …) are at most 11 bytes. The driver's other pushes are
  booleans, numbers and `nil`.
- So the program text is the one push that can be large.

**Proposed fix:** check the room before the text reaches Lua.
- `Sandbox.load` compares `get_memory_used() + len(text in UTF-8) + LOAD_HEADROOM` with
  `get_max_memory()`.
- When the text does not fit, it first runs a full collection, through a function that the set-up chunk
  returns, so no string is pushed. It checks again.
- If the text still does not fit, it raises `ProgramLoadError("not enough memory for the program text")`.
  The run then ends `failed`/`error` with that text, like any program that does not load.
- **The regression tests run in a child process,** so a regression fails the test instead of killing
  pytest:
  - a 3 MiB text under a 2 MiB cap;
  - a 5000-byte text swapped in when only 1000 bytes are left.

### 2. 🟡 LOW — `explorer.lua` and `explore.lua` are easy to confuse

**Where:** `programs/explorer.lua` (v2.4), `programs/explore.lua` and `programs/finish.lua` (v2.5).

**Failure scenario:** at the owner test, the owner ran `explorer.lua` with `finish.lua` swapped in.
- `explorer.lua` reports its map in the give-up text and writes nothing to `memory`.
- So `finish.lua` gave up with `no map in memory`.
- The run log showed exactly that, but the names differ by one letter, and the message does not say which
  program leaves the map.

**Proposed fix:**
- rename `explorer.lua`, for example to `map_as_text.lua`;
- make `finish.lua`'s message `no map in memory: swap it in after explore.lua`.

The owner was offered both and released without choosing, so this goes to the backlog.

## Fixes applied

### #1 — A program text is refused when it does not fit (9e325ca)

**The change:** `golem/interp/sandbox.py`.
- `Sandbox.load` compares the text's UTF-8 size plus `LOAD_HEADROOM` (4096 bytes) with the room left
  under the cap: `get_max_memory() - get_memory_used()`.
- When the text does not fit, it first runs a full collection, through a `collect` function that the
  set-up chunk returns, so no string is pushed. It checks again.
- If the text still does not fit, it raises `ProgramLoadError("not enough memory for the program text")`.
  The run ends `failed`/`error` with that text, at the start of a run or at a swap (where it counts as a
  version).

**The tests:** `tests/test_sandbox.py`.
- `test_a_program_text_larger_than_the_memory_cap_is_refused_not_a_crash`: a 3 MiB text under a 2 MiB
  cap, run in a child process.
- `test_a_swapped_in_text_that_does_not_fit_in_the_room_left_is_refused_not_a_crash`: a 5000-byte text
  swapped in with 1000 bytes left, in a child process.
- `test_garbage_is_collected_before_a_text_is_refused`: 1.2 MB of garbage with the automatic collector
  stopped; an 850 KB text fits only after the collection, and it loads.
- **Mutation checks:** without the check, the two child runs abort and both tests fail, while pytest
  survives. Without the collection, the garbage test fails.

**The verification:**
- The final gates: ruff clean, 706 tests passed.
- Live, `LUA_MAX_MEMORY=2097152 uv run golem-local run training/tier1/t1-01 <3 MiB program>` printed
  `"error": "not enough memory for the program text"` with exit 0, where it used to abort.
- The same text swapped in after `explore.lua` ended the same way, with versions [1, 2].

## Architecture impact

- **ARCHITECTURE §Execution, budgets and the report:** `error` can now be `"not enough memory for the
  program text"`, for a text that does not fit in the free memory under the cap. Such a text is refused
  before it reaches Lua, at the start of a run or at a swap.
- **For v4.1, which completes the sandbox:** lupa's pushes into Lua are unprotected.
  - Any new Python-to-Lua value that can be large must be checked the same way.
  - Today the program text is the only such value. The robot's results are short strings, booleans or
    numbers; the probe showed that 200-byte pushes survive with 8 bytes of room.

## What's solid

- **`memory` and the counters carry over by construction.**
  - `memory` is one table per runtime from the set-up chunk.
  - The counter lives in the driver chunk's closure, and a swap hands that closure the new chunk.
  - The mutation checks show that a reset counter, or an old coroutine left open, is caught.
- **The swap's refusals are decided from state, not from text.** A program's own `error("not enough
  memory", 0)` remains swappable; only a failure outside the program breaks the run.
- **One swap rule.** `swap_on_give_up` serves both `golem-local --swap` and the program route, so they
  cannot drift apart.
- **The frames and the swaps are deterministic.** A swapped run, a swapped route and the swapped
  command each give byte-identical output twice. Every new JSON key has a fixed order.
- **The sandbox is unchanged.** Neither program reaches the driver's functions, `coroutine`, `debug` or
  `_G`, before or after a swap.
- **No program text reaches the server log.** The log names the swap's step and the program's file name,
  which passes the name pattern. Give-up reasons and errors go only to the page, through `textContent`.
