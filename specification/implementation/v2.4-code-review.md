## Findings

### 1. 🟡 LOW — Overlapping runs leave a playback timer running

**Where:** `golem/screen/screen.js`, `runProgram`, `updateRunButton` and `startPlayback`.

**Failure scenario:**
1. `runProgram` disables Run while its request is in flight. But `updateRunButton()` runs again on the
   way: clicking a program (`showProgram`), changing the level select, or a reconnect that reloads the
   levels.
2. Each of these enables Run again, so the owner can send a second run before the first one answers.
3. The first answer starts a playback with its `setInterval`. The second answer calls `startPlayback`,
   which replaces `playback` without clearing that timer.
4. Both timers now advance the second playback, at double speed. When it ends, `finishPlayback` clears
   only its own timer and sets `playback` to `null`.
5. The first timer keeps firing. It throws a `TypeError` every 150 ms and doubles the speed of every
   later playback, until the page is reloaded.

The node harness showed it: Run was enabled while the first run was in flight, and after both playbacks
had ended, one timer was still running and had thrown 26 errors.

The window is narrow, since the example runs answer within milliseconds. A tier-three budget of 10 million
instructions, or a program that hits R1, widens it.

**Proposed fix:**
- keep Run disabled while a run is in flight (a `running` flag that `updateRunButton` respects);
- have `startPlayback` stop any earlier playback first.

The test checks both in the script's text, as the other tests of `screen.js` do. The node harness is run
again and not committed.

### 2. 🟡 LOW — README is behind the phase

**Where:** `README.md`, the status line and the "how to run" part.

**Failure scenario:** after the release, README still says that v2.4, "Lua programs run from the web
page, is next". A reader has no pointer to `programs/`, to the programs panel, or to `GOLEM_PROGRAMS_DIR`.

**Proposed fix:**
- mark v2.4 built in the status line, and name v2.5, the swap, as next;
- add a short paragraph on the programs panel: the folder, the name rule, the first-line description,
  and that a reload shows a changed or added program.

### 3. 🟡 LOW — Out-of-order program answers

**Where:** `golem/screen/screen.js`, `showProgram`.

**Failure scenario:** the owner clicks program A, then B. A's answer arrives last, so A's code is shown and
A is the one marked. The page stays consistent with itself: the code shown, the program marked and the
program that Run runs are all A. But it is not the program clicked last. On a local server the answers
come within milliseconds, so this is hard to hit.

**Proposed fix:** keep a request counter and drop an answer that is not the latest. It belongs with the
designed screen's panel in v3.2, which replaces this drawing.

### 4. 🟡 LOW — One bad file breaks the listing

**Where:** `golem/server/programs.py:30-39`, `list_programs`.

**Failure scenario:** a file in `programs/` that cannot be read, such as `chmod 000 x.lua` or a file removed
between the directory scan and the read, raises an `OSError`. `GET /api/programs` then answers `500
internal`, and the panel shows no program at all.

Each listing also reads every file in full only to take its first line, so a very large `.lua` slows every
reload. The folder is the owner's own, so neither happens by accident often.

**Proposed fix:** catch `OSError` per file and leave that file out, and read only the first line (capped)
for the description.

## Cross-checks against the specification

- **R1** (C functions without the count hook) is still open. It now reaches a worker thread of the server
  through a program in `programs/`. The owner decides it before v4.1, per ARCHITECTURE §Open decisions.
- **A DNS-rebinding page** could read the example programs and start runs. The `Host` check of v2.2 review
  #4 is planned for v5.1, and it covers these routes too.
- **The agent cannot reach these routes.** From v6 its only tool is the `golem` CLI, which has no command
  for programs, and the folder is in the repository, outside the agent's workspace.
- **The journal (v5.2) does not record these runs.** The screen's runs are the owner's experiments, outside
  any session. When v5.2 defines what the journal keeps, it should say so explicitly.

## What's solid

- **Program names are not paths.** A name pattern, a length cap and a resolved parent that must equal the
  folder refuse every escape tried: `..` raw or percent-encoded, separators, upper case, a symlink out of
  the folder, and a non-file.
- **The hidden levels stay hidden.** A run accepts only an id in the training list, so a hidden id gets
  the same `404 unknown_level` as a missing one. The test checks the reply against a fixture hidden
  level's lines.
- **The frames come from the core.** `on_move` takes the world that the core returned and renders it with
  `core.render`, so the page draws maps and decides nothing. A bump is a frame with a counted step, and
  `look`, `here` and `boxes_left` add none.
- **The frames are bounded and deterministic.** There are at most `step_budget + 1` frames, the report is
  identical to `run_program`'s, and a run gives byte-identical JSON twice (`test_driver.py`,
  `test_server_programs.py`).
- **Runs stay off the event loop.** The routes are plain `def`, so the human game's WebSocket keeps
  answering during a run, and every run has its own Lua runtime.
- **The page writes only text.** Code, descriptions, reports and error details all go through
  `textContent`, so nothing from a program can inject markup.
- **The keys stay where they belong.** The arrows in the level select never move the robot.

## Fixes applied

### #1 — One run and one playback at a time (4123cd4)

**The change:** `golem/screen/screen.js`.
- A `running` flag is set while a run request is in flight. `updateRunButton` keeps Run disabled while it
  is set, and `runProgram` refuses to start a second run.
- `startPlayback` calls `stopPlayback()` first, so a replaced playback's timer is always cleared.

**The test:** `tests/test_server_screen.py::test_one_run_and_one_playback_at_a_time`.
- It checks the script's text, as the other tests of `screen.js` do: the flag in `updateRunButton` and
  `runProgram`, the flag set before the request and cleared in `finally`, and `stopPlayback()` before a
  new playback.
- It fails on the old script.

**The verification:**
- The throwaway node harness, run again: Run stays disabled while a run is in flight, and after the
  playback no timer is left and no error is thrown.
- A normal run still plays to its last frame and shows the report, and Run is enabled again afterwards.

### #2 — README covers v2.4 (b4384e3)

**The change:**
- `README.md`: the status line marks v2.4 built and v2.5 next. A new section, "Programs on the page",
  covers the folder, the name rule, the description line and the reload.
- The `golem-local` example now uses `programs/t1_solver.lua`.
- The release-version skill now says to keep README's `Status:` line from calling a released phase next.

**The test:** `tests/test_roadmap.py::test_the_readme_never_calls_a_released_phase_next`.
- It fails when README's next phase is at or below `VERSION`, or its list of built phases is behind
  `VERSION`.
- With the old README and `VERSION` set to `2.4.0`, it failed with "README calls v2.4 next".

**The final gates:** ruff clean, 618 tests passed.
