# v2.3 — Issues

Issues for phase **v2.3 — Lua runs: the lupa spike, a minimal sandbox and the driver** (version **v2 —
Prototype: a text game screen, Lua runs and the program swap**), derived from the Tasks and DoD in
[ROADMAP.md](../ROADMAP.md) §v2.3 and the contracts in [ARCHITECTURE.md](../ARCHITECTURE.md). This file
covers one phase; ids continue from the previous phase (GOLEM-017 → **GOLEM-018…021**).

The phase makes a hand-written Lua program drive the robot through the core, one command at a time, within
its step and instruction budgets. It opens with a spike that confirms lupa, then builds a minimal but safe
sandbox, the driver with the short report, and `golem-local run`. The swap and `memory` across programs come
in v2.4. The deterministic `pairs`, `tostring`, `string.format`, `table.sort` and `math.random`, and the full
report, come in v4.1. The stops come in v4.2.

**Reconciled with the code (v2.2.0, commit 5ef5886):**
- **The interpreter:** there is no `golem/interp/` and no `golem/local.py` yet. `pyproject.toml` has no
  `lupa` and only the `golem-server` script.
- **The core** (`golem/core/`):
  - `world.py`:
    - `new_world(level, budget)`;
    - `move(world, dir) -> (world, moved)`, where an invalid direction is a `ValueError`;
    - `look(world, dir)`, which gives `"wall"`, `"box"`, `"goal"`, `"box_on_goal"` or `"empty"`;
    - `here(world)`, which gives `"goal"` or `"empty"`;
    - `boxes_left(world)` and `render(world)`;
    - `World.steps`, `.step_budget`, `.status` (`playing`, `solved` or `lost`) and `.loss_reason`
      (`steps`, `deadlock` or `instructions`; `LOSS_REASONS` already holds `instructions`).
  - `levels.py`: `levels_root()`, `list_levels(set, root)`, `load_level(id, root)`, `load_budgets(root)`
    and `budget_for(id, budgets)`. A `Budget` has `steps` and `instructions` (tier1: 200 and 1 000 000).
- **`.env.example`** names `GOLEM_LEVELS_DIR`, `GOLEM_HOST` and `GOLEM_PORT`, and
  `tests/test_server_app.py::test_env_example_names_the_server_variables` pins that set exactly. Adding
  `LUA_MAX_MEMORY` and `HOOK_EVERY` updates that test.
- **Recorded solutions** exist in `tests/fixtures/solutions/training/tier1/` (t1-01: `EE`; t1-02:
  `NNWNE`).
- **The design docs** need no correction: the v2.2 code review's "Architecture impact" touches only the
  screen routes. ARCHITECTURE §Robot language and §Execution describe the full v4.1 sandbox; v2.3 builds
  the subset that ROADMAP §v2.3 names.
- **Reconnaissance before the issues:** `lupa` 2.8 installs from a wheel on macOS arm64 with Python 3.12,
  and `lupa.lua54.LuaRuntime(register_eval=False, register_builtins=False, max_memory=…)` starts and
  reports `Lua 5.4`. Everything else is the spike's job.

### GOLEM-019 — The minimal sandbox: the runtime, the environment and the robot API wrappers

**Description:**
`golem/interp/sandbox.py` creates the Lua runtime and the program's environment for one run. It holds the
robot API as Lua wrappers that yield to the driver, `memory`, and only the allowlist names whose behaviour is
already deterministic. It also loads the program text. Touches `golem/interp/__init__.py`,
`golem/interp/sandbox.py`, `golem/interp/config.py`, `.env.example`, `tests/test_sandbox.py`,
`tests/test_server_app.py` (the `.env.example` names) and `specification/ARCHITECTURE.md`.

**What needs to be done:**
- **`golem/interp/config.py`:**
  - `InterpSettings(lua_max_memory, hook_every)` and `load_interp_settings(environ)`, a pure function over a
    mapping, like the server's settings;
  - defaults: `LUA_MAX_MEMORY` = 64 MiB, `HOOK_EVERY` = 1000;
  - a non-integer or non-positive value is a clear error.
- **The runtime:** `lupa.lua54.LuaRuntime(register_eval=False, register_builtins=False,
  max_memory=settings.lua_max_memory)`, one per run. No Python object is ever passed into Lua: the sandbox
  sets the environment up by running Lua code, and passes only strings and numbers.
- **The environment:** a fresh table, never `_G`, built in Lua. It holds:
  - the robot API: `move`, `look`, `here`, `boxes_left` and `give_up`;
  - `memory`, one plain table per runtime;
  - `assert`, `error`, `ipairs`, `select`, `tonumber`, `type`, and `unpack` (= `table.unpack`);
  - `string` without `dump` and `format`;
  - `table` without `sort`;
  - `math` without `random` and `randomseed`.

  The library tables are fresh copies, so the program cannot change the driver's own `string`, `table` or
  `math`.
- **The strings' metatable:** its `__index` becomes the trimmed string table, so `("").dump` and
  `("").format` are `nil`.
- **Wait for v4.1:** `pairs`, `tostring`, `string.format`, `table.sort` and `math.random`, in their
  deterministic versions.
- **Absent:** everything else in ARCHITECTURE's list, including `next`, the metatable functions, `pcall`,
  `coroutine`, `load`, `debug`, `require`, `io`, `os`, `print` and `python`.
- **The robot API wrappers** (Lua, closing over `coroutine.yield`, which the program cannot reach):
  - `move(dir)` and `look(dir)` check that `dir` is `"N"`, `"E"`, `"S"` or `"W"`. Anything else is a Lua
    error raised at the caller's line (`error(msg, 2)`).
  - `here()` and `boxes_left()` take no argument.
  - `give_up(reason)` requires a string, and anything else is a Lua error at the caller's line. It yields
    `{cmd = "give_up", arg = reason}` and never returns.
  - Each wrapper yields `{cmd = <name>, arg = <arg or nil>}` and returns what the driver resumes it with.
- **Loading:**
  - `load_program(runtime, env, source)` loads the text with `load(source, "=program", "t", env)`.
  - It returns the chunk, or the syntax error message with its `program:<line>:` prefix.
  - Bytecode is refused by the mode.
- **`.env.example`:** add `LUA_MAX_MEMORY` and `HOOK_EVERY` with one-line comments, and update the pinning
  test's expected set.
- **ARCHITECTURE:**
  - §Robot language and the sandbox: add one sentence that until v4.1 the environment holds the subset
    above, without `pairs`, `tostring`, `string.format`, `table.sort` or `math.random`;
  - in the robot API table, `give_up`'s reason must be a string; anything else is a Lua error, like an
    invalid direction.

**Dependencies:** GOLEM-018

**Expected result:**
A program loaded in the sandbox sees exactly the allowed names, and its robot commands yield `{cmd, arg}`
to whoever resumes it.

**Acceptance criteria:**
- [ ] **Tests** (`tests/test_sandbox.py`, real lupa):
  - each of `python`, `io`, `os`, `require`, `load`, `loadstring`, `dofile`, `loadfile`, `debug`, `pcall`,
    `xpcall`, `coroutine`, `next`, `rawget`, `rawset`, `rawequal`, `rawlen`, `setmetatable`,
    `getmetatable`, `collectgarbage`, `print`, `package`, `_G`, `pairs`, `tostring`, `string.dump`,
    `string.format`, `table.sort`, `math.random` and `math.randomseed` is `nil` inside a program;
  - `("").dump` and `("").format` are `nil`;
  - a bytecode chunk (made by the test with the runtime's own `string.dump`, outside the environment) is
    refused;
  - the allowed names work;
  - a program that assigns `string.upper = nil` does not change the driver's `string`;
  - `memory` is a plain table;
  - each command yields `{cmd, arg}`;
  - an invalid direction and a non-string `give_up` reason raise a Lua error naming the program's line;
  - a syntax error comes back with `program:<line>:`;
  - `load_interp_settings` covers the defaults and the bad values.
- [ ] **Determinism:** the same program, loaded in two fresh runtimes, yields the same sequence of commands.
- [ ] **Contract:**
  - the sandbox (the v2.3 subset and the `give_up` argument rule) and the `.env.example` names are updated

  - they are pinned by `tests/test_sandbox.py` and the updated `.env.example` test.
- [ ] **Gates:** lint and tests green.

### GOLEM-020 — The driver and the short report: commands, budgets, errors and endings

**Description:**
`golem/interp/driver.py` runs one program on one level. It resumes the program's coroutine, applies each
command through the core, counts instructions with the hook, and ends the run in exactly one way.
`golem/interp/report.py` turns the ending into the short report. Touches `golem/interp/driver.py`,
`golem/interp/report.py`, `tests/test_driver.py` and `tests/test_report.py`.

**What needs to be done:**
- **`run_program(level, budget, source, settings) -> dict`,** the short report:
  - one runtime;
  - the sandbox from GOLEM-019;
  - the program wrapped in a coroutine;
  - the count hook `debug.sethook(co, hook, "", HOOK_EVERY)` installed by a small driver chunk that holds
    `debug` and the sentinel in its upvalues. Neither is ever in the program's environment.
- **The loop:** resume the coroutine with the last result, receive `{cmd, arg}`, and apply it through the
  core:
  - `move` → `core.move`, result `true` or `false`;
  - `look` → `core.look`;
  - `here` → `core.here`;
  - `boxes_left` → `core.boxes_left`;
  - `give_up` → the run ends.

  After every `move`, a world that is `solved` or `lost` ends the run at once, and the program is not
  resumed.
- **The instruction budget:**
  - the hook adds `HOOK_EVERY` to the run's counter on every call;
  - when the counter reaches the level's `instructions` budget, the hook raises the sentinel;
  - the driver recognizes it in Lua with `rawequal` and ends the run as `lost` on `instructions`;
  - a program's own `error("instruction budget exhausted")` is an ordinary error.
- **The endings,** each giving one report:

  | Ending | `status` | `reason` | `error` |
  |---|---|---|---|
  | the level is solved | `solved` | `null` | `null` |
  | lost on steps or on deadlock (from the core) | `lost` | `steps` / `deadlock` | `null` |
  | the instruction budget is spent | `lost` | `instructions` | `null` |
  | `give_up(reason)` | `failed` | `give_up` | the reason, decoded as UTF-8 with replacement and cut to 200 characters |
  | the program returns | `failed` | `give_up` | `"program ended"` |
  | a Lua error, at load or at run time | `failed` | `error` | the message with its `program:<line>:` |
  | the memory cap | `failed` | `error` | `"not enough memory"` |
  | a Python exception in the driver | `failed` | `internal` | `"internal error"` (the traceback goes to the `golem.interp` log only) |

  An error value that is not a string becomes a short fixed text naming its type, never an address.
- **`report.py`:** `short_report(level_id, world, instructions, ending) -> dict`, a pure function over plain
  data. The keys come in this order: `level`, `status`, `reason`, `steps`, `instructions`, `error`. These
  are the run report's first six fields (ARCHITECTURE §Execution, budgets and the report); v2.4 and v4.1
  add the others.
- **No stops:** they come in v4.2. Every ending closes the run.

**Dependencies:** GOLEM-019

**Expected result:**
Any Lua program on any training level ends in exactly one short report, and the process survives every
ending.

**Acceptance criteria:**
- [ ] **Tests** (`tests/test_driver.py`, real lupa; programs inline in the tests):
  - a program that plays `t1-01`'s recorded solution with `move` ends `solved` with the core's step count;
  - `look`, `here` and `boxes_left` return the core's answers;
  - moves into a wall use up the step budget and end `lost`/`steps`;
  - a push into a corner ends `lost`/`deadlock`;
  - `while true do end` ends `lost`/`instructions`, with `instructions` at the budget (within
    `HOOK_EVERY`);
  - a loop that also calls `look` ends the same way;
  - `error("instruction budget exhausted")` ends `failed`/`error`;
  - `give_up("x")` ends `failed`/`give_up` with error `"x"`, and a 500-character reason is cut to 200;
  - a returning program gives `"program ended"`;
  - a syntax error and a run-time error carry their line;
  - `error({})` gives the fixed text;
  - a small `LUA_MAX_MEMORY` with a large `string.rep` ends `failed`/`error` with `"not enough memory"`, and
    a following run works;
  - a core function patched to raise ends `failed`/`internal`, and the next run works.
- [ ] **Tests** (`tests/test_report.py`): `short_report` over plain data, for every ending, with the key
      order.
- [ ] **Determinism:** each of the programs above, run twice in fresh runtimes, gives byte-identical
      `json.dumps` reports.
- [ ] **Contract:** the short report is the run report's first six fields, as in ARCHITECTURE. `internal` is
      added to `status: failed`'s reasons in §Execution, budgets and the report (it is already in §Error
      handling), and pinned by `tests/test_report.py`.
- [ ] **Gates:** lint and tests green.
