the server's WebSocket and the game screen**), derived from the Tasks and DoD in [ROADMAP.md](../ROADMAP.md)

## v2.1 — The server and the human game over WebSocket

### GOLEM-011 — The server skeleton: configuration, logging and `golem-server`

**Description:**
The server process: `create_app()`, its settings from the environment and `.env`, the rotating log, the
JSON error body, and the `golem-server` command bound to loopback only. Touches `pyproject.toml`, `uv.lock`,
`.env.example`, `golem/server/__init__.py`, `golem/server/config.py`, `golem/server/app.py`,
`tests/test_server_app.py` and `specification/ARCHITECTURE.md`.

**What needs to be done:**
- **Dependencies:**
  - runtime: `fastapi`, `uvicorn` and `python-dotenv`;
  - dev: `httpx`, which FastAPI's `TestClient` needs.

  Refresh `uv.lock`, and keep `golem/core` free of all of them (`tests/test_core_imports.py`).
- **`golem/server/config.py`:** a frozen `Settings` (`host`, `port`, `levels_dir`, `log_dir`) built by a pure
  `load_settings(environ)` over a mapping.
  - `GOLEM_HOST` defaults to `127.0.0.1`. A host other than `127.0.0.1`, `localhost` or `::1` is refused
    (CLAUDE.md: nothing in this project listens on the network).
  - `GOLEM_PORT` defaults to `8700`; anything but an integer from 1 to 65535 is refused.
  - `GOLEM_LEVELS_DIR` defaults to `levels`. It is resolved to an absolute path once, at load time.
  - The log goes to `data/logs`. `GOLEM_DATA_DIR` is v5.2's, so it is not read yet.
- **`create_app(settings)`** in `golem/server/app.py`:
  - **Refuse to start (v1 code review #4):** when `<levels_dir>/training` is missing, or `budgets.toml`
    doesn't load, raise one clear error that names the path.
  - Store the settings on `app.state`.
  - Every error response, including FastAPI's own 404 and 422, is
    `{"error": "<code>", "detail": "<text>"}` (ARCHITECTURE §HTTP API).
- **Logging:**
  - the `golem` logger writes to `<log_dir>/server.log`, rotating at 1 MB × 3, and to the console;
  - the log directory is created if missing;
  - nothing logs a level's text or a token.
- **`main()`:**
  - read `.env` with python-dotenv, without overriding the environment;
  - build the settings and the app;
  - run uvicorn on `host:port`.

  Register `golem-server = "golem.server.app:main"` in `[project.scripts]`.
- `.env.example`: add `GOLEM_HOST=127.0.0.1` and `GOLEM_PORT=8700`, each with a one-line comment.
- ARCHITECTURE.md:
  - §Configuration and secrets: `.env` is read by `golem-server` at start, the host is loopback-only, and the
    levels directory is resolved once and must exist;
  - §Repository layout: `server/config.py`.

**Dependencies:** None

**Expected result:**
`uv run golem-server` starts on `127.0.0.1:8700`, writes `data/logs/server.log`, and refuses a non-loopback
host or a missing levels directory with a clear message.

**Acceptance criteria:**
- [ ] `load_settings({})` gives `127.0.0.1`, `8700`, an absolute `levels` path and `data/logs`.
- [ ] **Tests** (`tests/test_server_app.py`, in-process, no open port):
  - the defaults, and a check that the default bind is `127.0.0.1`;
  - a non-loopback host such as `0.0.0.0` refused, and a bad port refused;
  - `create_app` refusing a missing training directory and a broken `budgets.toml` (v1 code review #4);
  - an unknown route answering 404 with `{"error", "detail"}`;
  - the log file created under a `tmp_path` log directory.
- [ ] **Contract:** the `.env.example` names `GOLEM_HOST` and `GOLEM_PORT` and the error body are pinned by
      `tests/test_server_app.py`, and ARCHITECTURE.md is updated in the same commit.
- [ ] **Gates:** lint and tests green; `tests/test_core_imports.py` still passes.
- [ ] **Manual (owner), Claude may run it:** `uv run golem-server` starts and prints that it listens on
      `127.0.0.1:8700`. Check with `curl` and stop the server.

### GOLEM-012 — `GET /api/levels`: the training levels with their sizes and budgets

**Description:**
The first API route: the training level ids with their tier, size and budgets. The same route serves
`golem levels` in v5.1. Touches `golem/server/app.py`, `tests/test_server_levels.py`,
`tests/fixtures/hidden/tier1/h-01.txt` and `specification/ARCHITECTURE.md`.

**What needs to be done:**
- `GET /api/levels` returns `{"levels": [...]}`. Each entry is
  `{"id", "tier", "width", "height", "budget": {"steps", "instructions"}}`, sorted by id, built from
  `list_levels("training")`, `load_level` and `budget_for`.
  - Only the `training` set is listed; hidden levels never appear.
  - The response never carries a map.
- A training level that fails to parse is reported in the server log by id and returns `500`
  `{"error": "level_error", "detail": "<id>: …"}`. A broken committed level should never pass the tests,
  but the owner can edit levels while the server runs.
- `tests/fixtures/hidden/tier1/h-01.txt`: the first fixture hidden level, a small map made up for tests. The
  real hidden levels are never used.
- ARCHITECTURE.md §HTTP API: the response shape, with an example.

**Dependencies:** GOLEM-011

**Expected result:**
`curl -s http://127.0.0.1:8700/api/levels` lists `training/tier1/t1-01`…`t1-03` with their tier, size and
budgets.

**Acceptance criteria:**
- [ ] **Tests** (`tests/test_server_levels.py`, `TestClient`):
  - the route against the committed levels: ids, tiers, sizes and budgets match the level files and
    `budgets.toml`;
  - against a `tmp_path` levels root that holds the training levels plus a copy of the fixture hidden
    level: no hidden id appears, and no line of the fixture's map appears anywhere in the response body;
  - a broken training level gives `500` with the error body.
- [ ] **Contract:** the `/api/levels` JSON shape is written into ARCHITECTURE §HTTP API and pinned by
      `tests/test_server_levels.py`, in the same commit.
- [ ] **Gates:** lint and tests green.
- [ ] **Manual (owner), Claude may run it:** `uv run golem-server` starts, and
      `curl -s http://127.0.0.1:8700/api/levels` lists the training levels (the ROADMAP §v2.1 DoD).

### GOLEM-013 — The human game over the WebSocket `/ws`

**Description:**
The human game: the server holds one game, and a client plays it with `load`, `move` and `restart`
messages, each answered with the game's `state` or an `error`, over a connection that stays open. Touches
`golem/server/ws.py`, `golem/server/app.py`, `tests/test_server_ws.py` and `specification/ARCHITECTURE.md`.

**What needs to be done:**
- `golem/server/ws.py`: the `/ws` route and a small pure layer that turns a message and the current game
  into a reply and the new game, so that most of the logic can be unit-tested without a socket.
  - The game is held on `app.state`, one at a time (ARCHITECTURE §HTTP API): the level, its budget and the
    current `World`.
- Messages (ARCHITECTURE §HTTP API, WebSocket `/ws`):
  - `{"type": "load", "level": "<id>"}`:
    - only ids in `list_levels("training")` are accepted;
    - a hidden id, an unknown id and a non-string id (v1 code review #7) all get the same
      `unknown level` error, so the reply never tells a hidden id from a missing one;
    - the game starts with `new_world(level, budget_for(...))`.
  - `{"type": "move", "dir": "N"|"E"|"S"|"W"}` applies `move` through the core.
  - `{"type": "restart"}` starts the loaded level again.
- Every accepted message is answered with
  `{"type": "state", "level", "map": render(world), "steps", "budget", "status", "reason"}`.
- Every bad message is answered with `{"type": "error", "detail": "<short text>"}`, and the connection
  stays open. Bad messages:
  - text that isn't JSON, JSON that isn't an object;
  - an unknown or missing `type`, a missing or bad field;
  - an invalid direction;
  - `move` or `restart` before any `load`.

  The detail never echoes the raw message or a level's text.
- On connect, when a game is loaded, the server sends its current `state` first. A page that reconnects
  then finds the game where it was (ARCHITECTURE §Error handling: "the human game state stays in the
  server"). Add this to the WebSocket contract.
- Log loads and level ends (solved or lost, with the reason) by level id.
- The page never decides a rule: every state comes from the core.

**Dependencies:** GOLEM-011

**Expected result:**
A WebSocket client loads a training level, moves, restarts and receives states whose steps, status and map
match the core. Every bad message gets an `error`, and the connection survives it.

**Acceptance criteria:**
- [ ] **Tests** (`tests/test_server_ws.py`, `TestClient` WebSocket, no open port):
  - a scripted client loads `training/tier1/t1-01`, plays the recorded solution and receives, after each
    move, a state equal to the core's `replay` state at that step (map, steps, status, reason), ending
    `solved`;
  - `restart` returns the starting state; moves after the end change nothing;
  - the error paths: not JSON, not an object, unknown type, missing type, missing or non-string `level`,
    an unknown id, a hidden id (from the fixture hidden level in a `tmp_path` root), a bad direction, and
    `move` or `restart` before `load`;
  - after each error, a valid message on the same connection still works;
  - the hidden id's error equals the unknown id's error, and no line of the fixture's map appears in any
    reply;
  - a second connection receives the current state on connect.
- [ ] **Determinism:** the same messages give the same states on two fresh apps (compared as JSON).
- [ ] **Contract:** the WebSocket messages, the state on connect and the single `unknown level` error are in
      ARCHITECTURE §HTTP API, pinned by `tests/test_server_ws.py`, in the same commit.
- [ ] **Gates:** lint and tests green.
